# Встроенная поддержка

Форма «Помощь → Написать в поддержку» сохраняет обращения в Supabase. Владелец сервиса открывает `/admin.html` и видит карточки с датой, номером, ID точки, описанием и статусом. Доступны фильтры по статусу, типу, ID точки, дате и теме/полному UUID. Список содержит 25 обращений на страницу; история загружается по 100 событий.

Ответы и изменения статуса сохраняются в истории. Пользователь читает ответы и пишет уточнения во вкладке «Мои обращения». Сообщение пользователя возобновляет закрытое обращение. Счётчик непрочитанного проверяется каждые 30 секунд, пока административная панель открыта и вкладка активна. Фоновая доставка push/email не подключена. **Telegram остаётся параллельным каналом уведомлений:** при создании обращения Edge Function отправляет сообщение в служебный чат через серверные переменные `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` (также поддерживаются `SUPPORT_TELEGRAM_BOT_TOKEN` и `SUPPORT_TELEGRAM_CHAT_ID`). При сбое отправки обращение остаётся в Supabase, причина без секретов записывается в `telegram_delivery_error`. Статусы и ответы ведутся в админпанели; обращения не появляются автоматически в переписке ChatGPT.

## Доступ

- Администратор сервиса определяется существующим `pvz2_private.service_admins` через `pvz2_service_admin_access`. Сервер проверяет Supabase Auth и список на каждом административном запросе. Роль администратора точки не даёт доступа к панели сервиса.
- Владельцы и сотрудники используют существующие проверенные сеансы; для сотрудников проверяются активность, принадлежность команде, роль и завершение смены временного пароля. График и его серверная функция не меняются.
- Обращения после входа связаны с проверенной личностью, а не с email или указанным ID точки. Владельцы с email видят свои новые обращения после повторного входа и на другом устройстве. Сотрудник видит только собственные обращения.
- Для гостя генерируется отдельный случайный ключ браузера. В `localStorage` хранится только этот ключ; содержимое переписки туда не записывается. В отдельной закрытой таблице хранится только его SHA-256. Очистка данных браузера или другой браузер лишают гостя доступа к прежней переписке. После входа интерфейс показывает обращения аккаунта; гостевые доступны после выхода в том же браузере.
- Прежние обращения сохранены в админпанели. Они не назначаются пользователю по совпадению email: этого недостаточно для проверки владельца.

На всех таблицах поддержки включён RLS. `anon`, `authenticated` и `PUBLIC` не имеют доступа к таблицам и серверным RPC. Доступ выполняется только через Edge Function с серверным ключом. SQL-функции работают как `SECURITY INVOKER` и доступны только `service_role`. Отсутствие пользовательских RLS-политик здесь намеренно означает запрет прямого доступа. `verify_jwt=false` сохранён из прежней функции: используются отдельные сеансы приложения и гостевой доступ, а проверка реальных полномочий выполняется внутри обработчика.

## Защита

Создание ограничено пятью обращениями за час по IP и проверенному отправителю; ответы пользователя — 30 в час по отправителю и 60 по IP. Счётчики изменяются атомарно. Добавлены honeypot, ограничение размера запроса, серверная проверка полей и запрет произвольных origin. Параллельные ответы проверяют версию; UUID запроса предотвращает дубли при повторной отправке. Текст экранируется при показе. Запросы и секреты не выводятся в журнал.

Поля не собирают пароли, сеансы или диагностические дампы. Текст с распознаваемыми паролями `пароль: ...`, токенами, JWT, ключами API, ключами Telegram и кодами восстановления отклоняется до сохранения. Произвольный пароль без подписи автоматически распознать невозможно; форма явно просит не присылать секреты. Автоматической выгрузки данных сотрудников или графика в обращения нет.

## Изменения и проверки — 15 октября 2026

- Миграции `20261015121907_support_inbox.sql` и `20261015125230_support_conflict_response.sql` добавляют историю, закрытую связь отправителя, индикаторы чтения, ограничения частоты и транзакционные операции. Второй файл использует прикладную ошибку вместо SQLSTATE `40001`, которую API повторяет автоматически.
- Версия `pvz2-support` 17 первоначально отключила Telegram. Исправление возвращает уведомления о **новых** заявках без потери записи в базе, а `pvz-v2-rbac` теперь позволяет одному сотруднику занимать разные позиции смен в день (занятую позицию назначить повторно нельзя). Иные правила доступа, оплаты и истории не меняются.
- Семь серверных тестов: секреты, origin, валидация, чужие обращения, проверка allowlist, несовместимые сеансы и запрет подмены роли.
- Транзакционные проверки базы: RLS/GRANT, ограничение частоты, собственник, дубли, конфликт версий, история и возобновление. Тестовые записи отменены.
- Шесть браузерных сценариев на тестовых данных: `index.html`, `login.html`, `admin.html`, каждый на ширине 1440 и 390 пикселей. Проверены отправка, история, ответ, закрытие, сохранение черновика при обновлении, экранирование HTML и отсутствие горизонтального переполнения.
- Реальный API проверен на изолированной временной точке: гость, владелец и сотрудник создают/читают только свои обращения; ответ администратора через серверную транзакцию виден гостю; уточнение возобновляет обращение; повтор не создаёт дубликат; устаревшая версия получает HTTP 409. Чтение графика через прежнюю функцию успешно.
- Реальный allowlist проверен в транзакции с ролью `authenticated`: существующий администратор получает `true`, посторонний UUID — `false`. Вход в браузере под реальным аккаунтом администратора не выполнялся; административный интерфейс проверялся на тестовых данных, проверка HTTP-авторизации — серверными тестами.
- Проверка Supabase Advisors не добавила предупреждений уровня WARN к исходному состоянию. Информационные уведомления об RLS без политик ожидаемы для закрытых серверных таблиц.

Для повторной проверки: `deno test --allow-env tests/support.test.ts`; `tests/database.sql` выполняется в транзакции с откатом. `node tests/ui.cjs` требует установленный Playwright и локальный сервер на порту 8767. `tests/live_support.py` предназначен для контролируемых сквозных проверок: после них обязательно удалить только созданные QA-записи и временный файл ключей.

## Публикация и восстановление

Сайт публикуется существующим GitHub Pages из `main`. Перед публикацией сверить исходную ветку и проверить PR. После успешной сборки сравнить опубликованные HTML, JS и CSS с подготовленными файлами. Предыдущий фронтенд: коммит `8babdd80043164682624435eddbeebb76e46c8bf`.

При проблеме интерфейса вернуть прежние HTML/JS/CSS отдельным коммитом. Таблицы, новые обращения и историю не удалять: изменения базы аддитивны. Функцию поддержки откатывать только из сохранённой версии после проверки совместимости. Прежняя версия функции 15 снова включает Telegram; это следует учитывать при выборе восстановления. Секреты Telegram не используются новой функцией, но их удаление из настроек проекта в эту задачу не входило.
